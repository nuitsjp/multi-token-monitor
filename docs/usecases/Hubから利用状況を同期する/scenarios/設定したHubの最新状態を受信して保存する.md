# 設定したHubの最新状態を受信して保存する

- 種別: 主成功
- UI確認: 不要

## 開始条件
利用者がアプリケーションを起動する。

## 手順
| # | アクター | システム |
| --- | --- | --- |
| 1 | 利用者がアプリケーションを起動する | 接続設定ファイルを読み、必須項目・ID重複・URL形式を検証する。各HubのIDと表示名をDBへ登録し、同梱の価格一覧を価格表へ適用してから、Hubごとに独立したSSE接続を開始する |
| 2 | Hubが接続時の全体状態（snapshot）を送る | 形式と必須項目を検証し、受信元のHubに紐づけて最新状態と受信時刻を一括で保存する。日別の履歴を含むときは、そのHubの日別の集計行を、受け取った日付ごとに上書きまたは追加する。受け取っていない日付の保存済みの行は変えない。利用枠ごとに計測点を記録し、製品ごとの月換算上限額と支払額を当日の行に記録する。保存の確定後、閲覧側へ変更を通知する |
| 3 | Hubが全体更新（stats）を送る | 検証し、当該Hubの最新状態を全体置換して受信時刻とともに保存する。手順2と同じく日別の集計行を日付ごとに上書きまたは追加し、日別の履歴を含まないときは保存済みの日別の集計行を変えない。利用枠ごとに計測点を記録し、手順2と同じく月換算上限額と支払額を記録する。保存の確定後、閲覧側へ変更を通知する |
| 4 | Hubが鮮度更新（freshness）を送る | 検証し、保存済みの状態を読まずに、当該Hubの受信時刻とHubの更新時刻、通知に含まれる端末ごとの更新時刻と古さだけを更新する。利用量・利用枠・stats全体の受信データは変えない。保存の確定後、閲覧側へ時刻の更新を通知し、Hub IDと更新した時刻・古さを渡す |
| 5 | 利用者がアプリケーションを終了する | 全Hubの受信を止め、処理中の保存が確定してからDBを閉じる |

計測点の記録:
- 計測点は、受信時刻、枠の使用率、当該Hubの全端末について枠の提供元と同じツールの累計の推定コストの合計の組とする。
- 利用枠ごとに計測点を最大2つ保持する。1つ目はリセット周期の中で最初に記録した点とし、以後は変えない。2つ目は最新の点とし、記録のたびに置き換える。
- 受信時刻が前回記録した次のリセット時刻を過ぎた場合、または使用率が前回より減った場合は、保持している計測点を捨てて、今回の点を1つ目として記録し直す。次のリセット時刻は受信のたびに最新の値で記録し、値が変わっただけでは計測点を捨てない。
- 報告されなくなった利用枠の計測点は削除する。

月換算上限額の日次記録:
- 製品・月換算上限額・価格表・支払額は [月換算上限額の推移を表示する](../../月換算上限額の推移を表示する/README.md) の定義に従う。
- snapshot・statsを保存するたびに、同じトランザクションで、製品ごとの月換算上限額をHomeと同じ式で求め、アプリを動かしているPCの現地日付の行に上書きする。当日の行が無ければ追加する。
- 同じ行に、その時点で価格表から引いた支払額を書く。価格表にプランが無いときは、支払額を空にする。
- 月換算上限額が求まらない製品（候補の枠がすべてEstimatingまたはN/A）は、その日の既存の行を消さない。
- freshnessでは記録しない。報告されなくなった製品の過去の行は消さない。

価格表の適用:
- 起動時に、同梱の価格一覧（プランごとの月額と最終更新日時）を価格表と比べ、価格表に無いプランと、同梱の最終更新日時の方が新しいプランを書き込む。価格表の最終更新日時の方が新しいか同じプランは変えない。同梱の一覧に無いプランは消さない。

## 受け入れ条件
- 設定した全Hubから独立して受信し、初回と更新後の最新状態を、保存処理とは別のDB接続からHubごとに読み取れる。
- 状態を未受信のHubも、IDと表示名で識別できる。
- snapshot・statsの保存が確定するたびに、閲覧側の通知の受け口で変更の合図を受け取れる。合図には利用データ・URL・認証トークンを含まない。
- freshnessでは、受信時刻・Hubの更新時刻・端末の更新時刻と古さだけが変わり、利用量・利用枠は変わらないことを、保存処理とは別のDB接続から読み取れる。保存の確定後、閲覧側の通知の受け口で、変更の合図とは別の種別で時刻の更新を受け取れる。これにはHub ID・受信時刻・Hubの更新時刻・端末ごとのIDと更新時刻と古さだけを含み、利用量・URL・認証トークンを含まない。
- freshnessの保存では、保存済みの状態をDBから読まない。
- heartbeatでは保存も通知もしない。
- 同じリセット周期でsnapshot・statsを3回以上受信しても、利用枠ごとの計測点は2つを超えず、1つ目は最初の受信の値のまま、2つ目は最新の受信の値になることを、保存処理とは別のDB接続から読み取れる。
- 受信時刻が前回記録した次のリセット時刻を過ぎた場合と使用率が減った場合は、計測点がその受信の値1つだけになる。受信時刻が前回記録した次のリセット時刻より前なら、次のリセット時刻の値が変わっても1つ目の計測点は変わらない。
- freshnessでは計測点を変えない。
- 日別の集計行（日付、トークン数、推定コスト）は、受信のたびに、受け取った日付だけを上書きまたは追加する。同じ状態を2回受信しても、保存済みのトークン数が変わらないことを、保存処理とは別のDB接続から読み取れる。
- 受信した履歴に含まれない古い日付の保存済みの行が、受信後も消えず、値も変わらない。
- 日別の履歴を含まない受信では、保存済みの日別の集計行が消えない。
- snapshot・statsを同じ日に複数回受信すると、製品ごとの当日の行は1つで、月換算上限額と支払額は最後に求まった値になることを、保存処理とは別のDB接続から読み取れる。日付が変わった後の受信では、前日の行は変わらず、新しい日付の行が加わる。
- 月換算上限額が求まらない受信では、当日の既存の行が消えず、値も変わらない。freshnessでは日次記録の行が変わらない。
- 価格表にプランがある製品は、その時点の月額が支払額として記録される。価格表を後で変えても、記録済みの行の支払額は変わらない。価格表にプランが無い製品の支払額は空である。
- 起動時に、価格表に無いプランと同梱の最終更新日時の方が新しいプランだけが書き込まれ、価格表の最終更新日時の方が新しいか同じプランは変わらない。
