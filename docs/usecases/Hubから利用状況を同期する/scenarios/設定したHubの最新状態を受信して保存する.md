# 設定したHubの最新状態を受信して保存する

- 種別: 主成功
- UI確認: 不要

## 開始条件
利用者がアプリケーションを起動する。

## 手順
| # | アクター | システム |
| --- | --- | --- |
| 1 | 利用者がアプリケーションを起動する | DBに登録済みのHubのうち、URLと認証トークンがどちらも空でないものを読み、受信状態を「受信中」にする。URLまたは認証トークンが空のHub（移行前から登録されていたHub）は受信せず、受信状態は「再接続中」のままにする。Hubごとに独立したSSE接続を開始する。登録済みのHubが0件なら、接続せずにWebサーバーだけを起動する |
| 2 | Hubが接続時の全体状態（snapshot）を送る | 形式と必須項目を検証し、受信元のHubに紐づけて最新状態と受信時刻を一括で保存する。日別の履歴を含むときは、そのHubの日別の集計行を、受け取った日付ごとに上書きまたは追加する。受け取っていない日付の保存済みの行は変えない。利用枠ごとに計測点を記録する。保存の確定後、閲覧側へ変更を通知する |
| 3 | Hubが全体更新（stats）を送る | 検証し、当該Hubの最新状態を全体置換して受信時刻とともに保存する。手順2と同じく日別の集計行を日付ごとに上書きまたは追加し、日別の履歴を含まないときは保存済みの日別の集計行を変えない。利用枠ごとに計測点を記録する。保存の確定後、閲覧側へ変更を通知する |
| 4 | Hubが鮮度更新（freshness）を送る | 検証し、保存済みの状態を読まずに、当該Hubの受信時刻とHubの更新時刻、通知に含まれる端末ごとの更新時刻と古さだけを更新する。利用量・利用枠・stats全体の受信データは変えない。保存の確定後、閲覧側へ時刻の更新を通知し、Hub IDと更新した時刻・古さを渡す |
| 5 | 利用者がアプリケーションを終了する | 全Hubの受信を止め、処理中の保存が確定してからDBを閉じる |

計測点の記録:
- 計測点は、受信時刻、枠の使用率、当該Hubの全端末について枠の提供元と同じツールの累計の推定コストの合計の組とする。
- 利用枠ごとに計測点を最大2つ保持する。1つ目はリセット周期の中で最初に記録した点とし、以後は変えない。2つ目は最新の点とし、記録のたびに置き換える。
- 受信時刻が前回記録した次のリセット時刻を過ぎた場合、または使用率が前回より減った場合は、保持している計測点を捨てて、今回の点を1つ目として記録し直す。次のリセット時刻は受信のたびに最新の値で記録し、値が変わっただけでは計測点を捨てない。
- 利用枠が報告されなくなっても、その枠は、最後に記録した次のリセット時刻を過ぎるまで、利用枠として保持する。報告されない間、使用率・次のリセット時刻・計測点は最後に記録した値のままとする。保持している枠は、報告された枠と同じように、利用枠の一覧・推定上限額に含める。報告が途切れていることを示す区別は設けない。
- 保持している枠が再び報告されたときは、上の規則を、最後に記録した使用率と次のリセット時刻と比べて適用する（使用率が最後に記録した値以下で、受信時刻がその次のリセット時刻より前なら、1つ目の計測点を引き継ぐ）。
- 報告されていない枠は、そのHubの次のsnapshot・statsの保存で、受信時刻が最後に記録した次のリセット時刻を過ぎていれば削除する。次のリセット時刻を持たない利用枠は、報告されなくなった時点で削除する。Hubを削除したときは、そのHubの利用枠・計測点もすべて削除する。

## 受け入れ条件
- 登録した全Hubから独立して受信し、初回と更新後の最新状態を、保存処理とは別のDB接続からHubごとに読み取れる。
- 状態を未受信のHubも、IDと表示名で識別できる。
- URLまたは認証トークンが空のHubには接続せず、保存済みの状態を保持する。他のHubの受信は妨げない。
- snapshot・statsの保存が確定するたびに、閲覧側の通知の受け口で変更の合図を受け取れる。合図には利用データ・URL・認証トークンを含まない。
- freshnessでは、受信時刻・Hubの更新時刻・端末の更新時刻と古さだけが変わり、利用量・利用枠は変わらないことを、保存処理とは別のDB接続から読み取れる。保存の確定後、閲覧側の通知の受け口で、変更の合図とは別の種別で時刻の更新を受け取れる。これにはHub ID・受信時刻・Hubの更新時刻・端末ごとのIDと更新時刻と古さだけを含み、利用量・URL・認証トークンを含まない。
- freshnessの保存では、保存済みの状態をDBから読まない。
- heartbeatでは保存も通知もしない。
- 同じリセット周期でsnapshot・statsを3回以上受信しても、利用枠ごとの計測点は2つを超えず、1つ目は最初の受信の値のまま、2つ目は最新の受信の値になることを、保存処理とは別のDB接続から読み取れる。
- 受信時刻が前回記録した次のリセット時刻を過ぎた場合と使用率が減った場合は、計測点がその受信の値1つだけになる。受信時刻が前回記録した次のリセット時刻より前なら、次のリセット時刻の値が変わっても1つ目の計測点は変わらない。
- 利用枠がsnapshot・statsに含まれない受信を挟んでも、その枠の次のリセット時刻より前なら、利用枠の行と計測点が削除されず、使用率・次のリセット時刻・計測点が最後に記録した値のままであることを、保存処理とは別のDB接続から読み取れる。その枠は、閲覧側が読む利用枠の一覧・推定上限額に、報告された枠と同じように含まれる。
- 次の受信で枠が再び報告され、使用率が最後に記録した値以下なら、1つ目の計測点は変わらず、2つ目が最新の受信の値になる。
- 再び報告された枠の使用率が最後に記録した値より減っている場合、または受信時刻が最後に記録した次のリセット時刻を過ぎている場合は、計測点がその受信の値1つだけになる。
- 報告されなくなった枠は、受信時刻が最後に記録した次のリセット時刻を過ぎた後の、そのHubの最初のsnapshot・statsの保存で削除される。次のリセット時刻を持たない枠は、その枠が報告されなくなった受信の保存で削除される。
- Hubを削除すると、そのHubの利用枠・計測点も残らない。
- freshnessでは計測点を変えない。
- 日別の集計行（日付、トークン数、推定コスト）は、受信のたびに、受け取った日付だけを上書きまたは追加する。同じ状態を2回受信しても、保存済みのトークン数が変わらないことを、保存処理とは別のDB接続から読み取れる。
- 受信した履歴に含まれない古い日付の保存済みの行が、受信後も消えず、値も変わらない。
- 日別の履歴を含まない受信では、保存済みの日別の集計行が消えない。
- 起動時と snapshot・stats・freshness の保存時に、月換算上限額・支払額の日次記録とプランの価格表を作成・更新しない。
- アプリケーションの更新時に、保存済みの日次記録と価格表を削除する。Hubの登録情報、利用実績、端末別の日次モデル明細、契約、利用枠とその計測点は保持する。新規DBと更新後のDBに `daily_monthly_limits` と `plan_prices` は存在せず、再起動と受信後も再作成されない。
