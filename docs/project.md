# Token Monitor Analytics のプロジェクト定義

プロジェクト共通の要件・制約、ユースケース一覧、確認した事実、および実行・検証手順の正本です。全体構造は [アーキテクチャ](architecture.md) を参照します。

## 1. 目的と範囲

| 項目 | 内容 |
| --- | --- |
| 解決する問題・達成したい結果 | 私用・業務など別々の Token Monitor Hub に集約されたAIツールの利用状況を、Hubごとに開かずに1か所で確認できるようにする |
| 利用者・利用場面 | Hubを利用する本人が、自分のPCでアプリケーションを起動し、ブラウザーで閲覧する |
| 今回の対象 | 設定画面からのHubの登録（追加・変更・削除）、登録したHubからの最新状態の受信と保存、日次明細の取得と保存、月換算上限額と支払額の日次記録、プランの価格表の保持とアプリ更新時の適用、保存済み利用状況の閲覧 |
| 今回の対象外 | Hubへの書き込み（端末削除・サブスクリプション編集）、受信履歴の蓄積、接続設定ファイルからのHubの読み込み、利用者向けWeb認証、旧製品のDB移行と旧製品機能の暗黙の復元 |

## 2. 制約・品質要求・受け入れ条件

- WindowsまたはUbuntu 24.04上で、アプリケーションはループバックアドレス（127.0.0.1）だけで待ち受けます。単一の利用者が使い、利用者向けの認証は設けません。UbuntuでのLAN・TailscaleへのHTTP公開はManageMediaServerのnginxとホスト側ファイアウォールで行います。
- Hubの接続情報（表示名・URL・認証トークン）は、利用者が設定画面から登録してDBに保存します。接続設定ファイルは使いません。認証トークンはDBの値を除き、ログ、閲覧用のAPI、画面、通知に含めません。URLは設定画面にだけ表示し、他の画面・閲覧用API・ログ・通知に含めません。
- Hubごとの受信データは最新状態だけを保存し、受信履歴は保存しません。利用状況の変遷に使う日次明細はドメインモデルとして保存します。
- あるHubで障害が起きても、他のHubの受信とWebサーバーは止めません。
- UIの表示文言は、ツールチップと取得失敗メッセージを含め、すべて英語に統一します。トークン数と推定コストの数値表示は、Homeと各閲覧画面で共通の書式・更新動作を使います。具体的な動作と適用範囲は [UCP-2](design/UCP-2.md) に従います。
- 受け入れ条件は各シナリオに記載し、`mise run verify` の合格を完了の条件とします。

## 4. 確認した事実

- 対象のHubは [Javis603/token-monitor](https://github.com/Javis603/token-monitor) の固定版 `8b6cee22eabb7bf7ce0226655b46907300e14a04` です。`docs/API.md` によると、`GET /api/stats/stream` はSSEで次の3種類のイベントを送ります（2026-09-25に確認）。
  - `snapshot`: 接続時の全体状態
  - `stats`: 全体状態の置換
  - `freshness`: 時刻と鮮度情報だけの更新。要求ヘッダー `x-token-monitor-stream: 2` を付けた場合だけ送られます。
- 同じ固定版の `src/shared/clientCatalog.js` では、利用枠の提供元（`limits.providers[].provider`）とツール（`clientModels` のキー）が同じ識別子（`claude`・`codex` など）です（2026-09-27に確認）。推定上限額は、この一致で枠とツールの推定コストを対応させます。
- 旧リポジトリで取得した実Hubの応答資料には、アカウントや端末の情報が含まれます。そのためこのリポジトリには複製せず、必要になった時点で改めて測ります。

## 5. 実行・切り替え・検証手順

作業ディレクトリはリポジトリのルートです。コマンドはすべてここで実行します。

| 目的 | コマンド | 期待結果 |
| --- | --- | --- |
| 環境構築 | `mise run setup` | 固定版のNode.js・.NET・Pythonと、npm・NuGetの依存を導入します。`.env` がなければ `.env.example` から作成します |
| E2E用ブラウザーの導入 | `mise run setup:browser` | E2Eで使うChromiumを導入します |
| 開発起動 | `mise run dev` | `http://127.0.0.1:5173/` でVite（HMR）の画面を開けます。.NETは `.env` の `HOST`・`PORT`（既定 `127.0.0.1:3000`）で起動します |
| 配布物のビルドと起動 | `mise run start` | 起動のたびに `mise run build` で `dist/server` に配布物を作り直してから、`http://127.0.0.1:3000/`（`.env` の `HOST`・`PORT`）で画面とAPIを同じポートから配信します |
| 停止 | 起動したターミナルで Ctrl+C | 開発起動ではViteと.NETの両方が停止します |
| 全体検証 | `mise run verify` | API契約の一致、型検査、Lint、整形、文書検査、DBML構文検査、.NETとフロントエンドの単体テスト、開発構成と配布構成のE2Eがすべて合格します。環境変数 `E2E_MODES`（`dev`、`hosted`、またはカンマ区切り。既定は両方）でE2Eの構成を絞れます。CIはLinuxで両方、Windowsで `hosted` だけを実行します |
| 文書検査 | `python scripts/doc_check.py .` | NGが0件です |
| テーブル設計の構文検査 | `mise run check:dbml` | `docs/design/data.dbml` をDBMLとして解析できます。全体検証にも含まれます |
| Linux配布物の作成 | `bash scripts/package-linux.sh`（Linux x64で全体検証後） | `dist/package/` に画面を同梱した配布物とSHA-256を作成します。版とコミットを配布物に含めます。CIではUbuntuの全体検証に合格した場合だけ同じ成果物をアップロードします |
| 正式版の自動採番と発行 | `mise run release` | コミット済みのHEADへ `vX.Y.Z` の注釈付きタグを付け、originへpushします。取得した正式版タグと `package.json` の大きい版を基準に、パッチ番号を1つ増やします |
| 指定した版の発行 | `mise run release 0.2.0`（`v0.2.0` も可） | 指定版のタグをpushします。未コミットの変更、既存タグ、現在の版より古い指定は拒否します |

正式版タグのpushで発行ワークフローが起動し、Linux・Windowsの全体検証に合格してからLinux配布物とSHA-256をGitHub Releaseへ添付します。配布物の版はタグの値を使います。添付が完了するまではdraftにし、完了後に公開します。`package.json` の版は書き換えません。タグのpushが失敗した場合はローカルタグを保持し、表示したpushコマンドで再試行します。

Ubuntuホストでの直接配置、LAN・TailscaleへのHTTP公開、systemdによる起動、手動・日次更新は [ManageMediaServer](https://github.com/nuitsjp/ManageMediaServer) で管理します。アプリ本体はループバックで起動し、公開側のnginxで到達元とHostを制限して中継します。ホスト上ではビルドせず、検証済みのLinux配布物を使います。

Hub同期のE2E（`tests/e2e/Hubから利用状況を同期する/`）は、テストごとにBearerトークンを検証する偽Hubを立て、起動前のDBへそのURLとトークンのHubを登録して本番の受信・保存処理を通し、別の読み取り専用接続から保存値を照合します。
freshnessは、時刻と古さだけが変わることと `hub.freshness` の本文を照合し、保存済みの受信データを適用できない内容に書き換えても保存できることで、保存済みの状態を読まないことを確かめます。
利用枠の計測点は、偽Hubに残量・リセット時刻・推定コストを変えたstatsを順に送らせ、1つ目の計測点が最初の受信のまま引き継がれること、使用率の減少と前回のリセット時刻の経過で記録し直されること、freshnessで変わらないことを照合します。
再接続は、偽Hubに接続の終了・認証拒否・リダイレクト・不正な通知・保存に失敗する通知を返させ、ログの原因の分類と待ち時間、受信状態、通知の合図を照合します。待機中の終了は、終了の依頼から5秒以内に終わることで確かめます。
再起動は、同じDBと設定でアプリを停止・起動し直し、受信前の保存値の保持、受信状態の戻り、最初の全体状態での置き換えを照合します。

閲覧のE2E（`tests/e2e/利用状況を閲覧する/`）は、同じ偽Hubから本番の受信・保存処理でDBに状態を作り、画面の表示値を偽Hubの送った値から求めた期待値と照合します。
表示中の更新は、画面を開いたまま偽Hubに新しい状態を送って確かめます。鮮度更新の反映は、偽Hubに時刻の更新を送り、閲覧用APIを呼ばずに時刻と鮮度切れだけが変わることと、閲覧用APIの応答を止めている間に時刻の更新を受けても応答後に古い時刻へ戻らないことを確かめます。通知の再接続は、ブラウザー側で `/api/events` の最初の接続を切り、保存の後に再接続を本物のAPIへ通して確かめます。
推定上限額は、偽Hubに残量と推定コストを変えたstatsを送らせ、使用率の差が1ポイント未満の場合とコストが増えない場合は「Estimating」、条件を満たした場合は計算式どおりの金額、コストの範囲を確定できない場合は「N/A」を表示し、他のグループ・他のアカウントの利用で値が変わらないことを確かめます。月換算上限額は、円のラベルの「枠グループ名 金額/mo」と円弧に重ならない位置、見出し行の右端の契約の合計、値を持たないグループがあるときの「≥」と説明を確かめます。
再接続状況の表示は、接続できないHubと、表示中に偽Hubの接続を切って再接続を2回失敗させたHubで、目印の有無・説明・値を確かめます。
モデル情報を表示するE2E（`tests/e2e/モデル情報を表示する/`）は、外部の偽Hubから本番の受信・保存処理でDBに状態を作り、実APIを通じて表示した `/by-model` の値を、送った値から求めた期間合計・モデル別の値と照合します。既存の表示検証には2つの偽Hub（各2端末・7モデル・370日分）を使います。All・個別Hubの絞り込み、Tokens／Costの降順と同順位の名前順・コスト不明の最後への配置、初回・Hub変更・ソート変更での表示先頭5モデルの選び直し、個別Hub名横のConnected・Not received・Reconnectingの状態アイコンとTooltip、Allの状態アイコンなしを確かめます。Otherへの合算と色、三状態のSelect all、期間・集約単位の切り替えでの選択の保持、明細が無い期間の「—」、操作で取得し直さないこと、高さ640pxでの縦スクロールなしと一覧だけのスクロール、狭い幅での折り返しと横スクロールも確かめます。コスト不明・同順位・Otherの集計の境界は、フロントエンドの単体テスト（`tests/frontend-unit/model-usage.test.ts`）でも確かめます。
デバイス情報を表示するE2E（`tests/e2e/デバイス情報を表示する/`）は、同じ2つの偽Hub（各2端末）から作ったDBで、メニューのBy deviceから開いた `/by-device` の値を、送った値から求めたデバイス別・期間合計の値と照合します。メニューの並びとDevicesのサブメニューが無いこと、All・個別Hubの絞り込み、Tokens／Costの降順と同順位のホスト名順、先頭5デバイスの選び直し、Otherへの合算、三状態のSelect all、キーボード操作、期間・集約単位の切り替えでの選択の保持、明細が無い期間の「—」、操作で取得し直さないこと、鮮度を表示しないことを確かめます。偽Hubの1端末を別のHubと同じデバイスIDで報告させ、1つに合算して登録順で最初のHubのホスト名で示すことも確かめます。同じホスト名で別のデバイスIDを分けることとデバイスID順の並びは、単体テスト（`tests/frontend-unit/device-usage.test.ts`）で確かめます。
月換算上限額の推移を表示するE2E（`tests/e2e/月換算上限額の推移を表示する/`）は、偽Hubに約1か月の長さの枠と推定コストを送らせ、本番の受信・保存処理で当日の日次記録を作ります。同期側のシナリオ（`tests/e2e/Hubから利用状況を同期する/`）では、同じ日の受信で枠グループごとの当日の行が1つのまま最後に求まった値になること、価格表から大文字・小文字を区別せずに支払額を引くこと、価格表に無いプランの支払額が空であること、月換算上限額が求まらない受信と freshness で当日の行が変わらないこと、起動時に同梱の価格一覧を最終更新日時の新しい方だけ適用し、前日の記録が変わらないことを照合します。画面側では、1日1行のため同期では作れない過去の日の記録をDBへ直接書き込み、メニューからの移動、3M・Weeklyの初期表示と全契約の選択、契約の並びと色、枠グループを合計したタイルの値・N/Aの理由、記録のない枠グループがある日の下限値（ツールチップとタイルの「≥」、線を途切れさせないこと）、縦軸の0始まり、タイルとSelect allでの選択、週次の点がその週の最後の記録になること、4W・Dailyでの点の数と記録の無い日の途切れ、期間を戻したときの選択の保持、操作で取得し直さず保存の合図で取得し直すこと、記録が無いときの表示、高さ640pxでの縦スクロールなしとタイルだけのスクロールを確かめます。

接続するHubを管理するE2E（`tests/e2e/接続するHubを管理する/`）は、登録済みのHubが0件のDBから起動し、最初の全体状態を返さない偽Hubを画面から追加して確かめます。メニュー最下部のSettings、0件の表示、追加フォームを通常は表示しないこと、空・不正なURL・空のトークンでの項目ごとのメッセージと未保存、保存後の一覧の末尾への追加・DBの値・UUIDのID採番、再起動なしの受信開始（偽Hubへの接続数と認証拒否0件）、Not receivedからConnectedへの変化とBy hubへの反映、同じ表示名・URLの複数登録、保存後に接続が切れたHubのReconnectingと他のHub・Webサーバーの継続、認証トークンとURLが閲覧用API・通知・ログ・画面に出ないことを照合します。追加は、接続の確認を通らない入力（認証トークンの拒否・接続できない接続先）が保存されないことも確かめます。
Hubの登録情報を変更するE2E（同じディレクトリの `Hubの登録情報を変更する.spec.ts`）は、接続情報が空のHubと画面から追加したHubを、2つの偽Hubで変更して確かめます。ポップアップの初期値（認証トークンは空）と破棄、検証での未保存、表示名だけの変更が接続を試さず認証トークンを保つこと、認証トークンの拒否・接続できない接続先での未保存とメッセージ、変更後の同じIDでの更新と一覧の位置、変更前の接続の終了と変更後の接続先での受信開始と最新状態の置き換え、変更前の接続先へ再接続しないこと、空だったHubは認証トークンを入れて初めて受信を始めること、認証トークンとURLが閲覧用API・通知・ログ・画面に出ないことを照合します。
登録情報の検証・更新・移行と接続の確認は単体テスト（`tests/dotnet-unit/Features/HubRegistration/`、`tests/dotnet-unit/Infrastructure/Persistence/DatabaseTests.cs`）、変更での認証トークンの検証は `tests/frontend-unit/hub-form.test.ts` でも確かめます。

設定は `mise run setup` が作る `.env` に置きます。`HOST` は `127.0.0.1` または `::1` だけを受け付けます。DBは `DB_PATH`（既定 `./data/app.sqlite`）のSQLiteファイルで、起動時に作成・移行します。

Hubは設定画面（`/settings`）から登録し、接続情報（表示名・URL・認証トークン）をDBの `hubs` に保存します。接続設定ファイルと `HUB_CONFIG_PATH` はありません。起動時は、URLと認証トークンがどちらも空でないHubごとに受信を開始し、登録直後のHubは再起動なしに受信を開始します。登録済みのHubが0件でも起動します。起動後はHubごとに受信を開始し、保存と受信停止をHub IDと原因の分類だけでログに出力します。受信が止まったHubへは、待ち時間を1秒から倍にしながら（上限60秒）再接続を続けます。環境変数 `HUB_RETRY_TIME_SCALE`（0より大きく1以下、既定1）は、実際の待機だけに倍率をかけます。ログの待ち時間は変わりません。E2Eが待ち時間を縮めるための設定で、通常は指定しません。

開発構成は `mise run dev` で起動して `http://127.0.0.1:5173/settings`、配布構成は `mise run start` で起動して `http://127.0.0.1:3000/settings` を開きます。停止は起動したターミナルでCtrl+Cです。
